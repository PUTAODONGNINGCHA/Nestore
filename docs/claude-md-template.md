## 工作流规则（必读）

- **推送规则**：不要自动推送代码，只有用户明确说"推送"或"push"时才执行 git push。
- **先讨论再动手**：复杂功能、架构变更、UI 改动前，必须先讨论方案，用户确认后再实现。不要跳过讨论直接写代码。
- **简洁回应**：不要输出冗长的分析过程，直接给结论和可操作的方案。
- **单次改动聚焦**：一次只做一个功能/修复，完成后等用户反馈再继续下一步。

## 代码规范

### Git Commit 格式
```
<type>: <subject>

Type: feat / fix / docs / style / refactor / test / chore
```

### 核心约定
- 缩进：2 空格
- 命名：camelCase（变量/函数）、PascalCase（组件/类型）
- 类型：TypeScript 严格模式，禁止 any
- 注释：只在 WHY 不明显时写，不写 WHAT
