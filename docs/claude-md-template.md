## 工作流规则（必读）

- **推送规则**：不要自动推送代码，只有用户明确说"推送"或"push"时才执行 git push。
- **先讨论再动手**：复杂功能、架构变更前，必须先讨论方案，用户确认后再实现。
- **简洁回应**：直接给结论和可操作的方案，不输出冗长的分析过程。
- **单次改动聚焦**：一次只做一个功能/修复，完成后等用户反馈再继续。
- **完成后必须验证**：每个功能完成后验证可运行，不能只写完代码就当完成。

## 模式切换

> Shift + Tab 切换模式

| 模式 | 行为 |
|------|------|
| **自动模式** | AI 根据需要自动执行 |
| **Plan 模式** | 仅提供计划，用户确认后执行 |
| **Yolo 模式** | 直接执行，不确认 |

| 阶段 | 推荐模式 |
|------|----------|
| 需求讨论 | Plan 模式 |
| 架构分析 | Yolo 模式 |
| 代码开发 | 自动模式 |
| 问题修复 | Plan 模式（复杂）/ 自动模式（简单） |

## 代码规范

### Git Commit 格式
```
<type>: <subject>

Type: feat / fix / docs / style / refactor / test / chore
```

### 核心约定（按语言调整）

- 缩进：2 空格
- 命名：camelCase（变量/函数）、PascalCase（类/组件）
- 注释：只在 WHY 不明显时写，不写 WHAT
